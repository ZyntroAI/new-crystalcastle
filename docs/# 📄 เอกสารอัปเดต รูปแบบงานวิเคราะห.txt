## ภาพรวมรูปแบบ

### 💡 Antigravity คืออะไร?

**รูปแบบ Antigravity** คือรูปแบบการทำงานมาตรฐานที่พัฒนาขึ้นเพื่อให้เอเจนต์สามารถ **อ่านโครงการทั้งหมด → วิเคราะห์ → สร้างเอกสาร/แผน/รายงานที่มีคุณภาพสูง** ได้อย่างสม่ำเสมอและเป็นมาตรฐานเดียวกัน โดยไม่ต้องเขียนคำสั่งยาวๆ ซ้ำๆ ทุกครั้ง

### 🎯 คุณลักษณะสำคัญ

- ✅ **อ่านอัตโนมัติ:** สแกนไฟล์สำคัญทั้งโครงการด้วยตัวเอง
- ✅ **วิเคราะห์ลึก:** แยกโครงสร้าง, สถาปัตยกรรม, โดเมน, โฟลว์ข้อมูล
- ✅ **สร้างศิลปากร:** สร้างไฟล์ Markdown พร้อมเนื้อหาครบถ้วน
- ✅ **ตรวจสอบก่อน:** ตรวจสอบความถูกต้อง (Build/Compile) ก่อนเขียนแผน
- ✅ **นำเสนอให้ตรวจ:** แจ้งให้ทราบเมื่อสร้างเสร็จ รออนุมัติก่อนดำเนินต่อ

## โครงสร้างขั้นตอนมาตรฐาน

### 📌 ขั้นตอนที่ 1: รับคำขอ → ตรวจสอบความสามารถ
```
ผู้ใช้: "ตรวจสอบโครงการนี้ วิเคราะห์สถาปัตยกรรม และสร้างรายงาน"
เอเจนต์: ✅ รับทราบ — กำลังอ่านโครงสร้างโครงการ...
```

### 📌 ขั้นตอนที่ 2: สำรวจและอ่านไฟล์สำคัญ
- ค้นหาไฟล์สถาปัตยกรรมหลัก, รหัสต้นทาง, ไฟล์กำหนดค่า
- อ่านและสกัดข้อมูลสำคัญ: โมเดล, คอนโทรลเลอร์, คลาสหลัก, ฟังก์ชันหลัก
- บันทึกจำนวนไฟล์ที่อ่าน: `5 files read` / `8 files analyzed`

### 📌 ขั้นตอนที่ 3: ตรวจสอบความถูกต้อง (ถ้าเป็นไปได้)
```
✅ กำลังตรวจสอบการคอมไพล์...
✅ dotnet build เสร็จสิ้น / Build Succeeded
✅ ตรวจสอบโครงสร้างและการอ้างอิงถูกต้อง
```

### 📌 ขั้นตอนที่ 4: วิเคราะห์และจัดระเบียบเนื้อหา
- **สรุปผู้บริหาร + เทคสแต็ก** — ภาพรวมและเทคโนโลยีที่ใช้
- **โมเดลโดเมน / คลาสหลัก** — โครงสร้างข้อมูลและความสัมพันธ์
- **ส่วนประกอบสำคัญ** — คอนโทรลเลอร์, บริการ, เอนจิน, ชั้นข้อมูล
- **โฟลว์ข้อมูล** — ลำดับการทำงาน, การไหลของข้อมูล
- **คุณสมบัติพิเศษ** — แคช, ความถูกต้อง, การรวมระบบ, ฯลฯ

### 📌 ขั้นตอนที่ 5: สร้างไฟล์ศิลปากร (.md)
- ตั้งชื่อไฟล์ตามมาตรฐาน: `project_architecture_report.md` / `project_review.md` / `implementation_plan.md`
- เขียนเนื้อหาครบถ้วน มีหัวข้อชัดเจน
- แจ้งชื่อไฟล์ที่สร้างให้ผู้ใช้ทราบ

### 📌 ขั้นตอนที่ 6: นำเสนอและรออนุมัติ
```
✅ สร้างไฟล์ `implementation_plan.md` เรียบร้อยแล้ว
📋 ตรวจสอบแผนก่อน — เมื่ออนุมัติ ผมจะเริ่มพัฒนาตามแผนทันที
```

## รูปแบบผลลัพธ์และไฟล์ศิลปากร

### 📄 ประเภทของรายงานมาตรฐาน

| ชื่อไฟล์ | วัตถุประสงค์ | ส่วนประกอบหลัก |
|---|---|---|
| `project_architecture_report.md` | รายงานสถาปัตยกรรมเต็มรูปแบบ | สรุปผู้บริหาร, เทคสแต็ก, โมเดลโดเมน, โฟลว์ข้อมูล, แผนภาพ |
| `project_review.md` | รีวิวและวิเคราะห์ทางเทคนิค | ภาพรวม, สแต็ก, โมเดล, คอนโทรลเลอร์, การกำหนดค่า, ข้อสังเกต |
| `implementation_plan.md` | แผนการพัฒนา/ปรับปรุง | ขอบเขต, ขั้นตอน, โครงสร้างที่จะสร้าง, UI/UX, การทดสอบ |

### 📐 รูปแบบเนื้อหามาตรฐาน

```markdown
# ชื่อรายงาน — ชื่อโครงการ

## 1. ภาพรวมและเทคโนโลยี
> โครงการคืออะไร, วัตถุประสงค์, สแต็กเทคโนโลยีหลัก

## 2. โมเดลและโครงสร้างข้อมูล
> คลาสหลัก, ความสัมพันธ์, คุณสมบัติที่สืบทอด

## 3. ส่วนประกอบและการทำงาน
> คอนโทรลเลอร์, บริการ, เอนจิน, เมธอดสำคัญ

## 4. โฟลว์ข้อมูลและลำดับการทำงาน
> ข้อมูลไหลจากไหนไปไหน, ขั้นตอนการทำงาน

## 5. คุณสมบัติพิเศษและการกำหนดค่า
> แคช, การตรวจสอบ, การสร้างภาพ, การทดสอบ ฯลฯ

## 6. ขั้นตอนถัดไป
> แนะนำสิ่งที่ควรทำต่อ
```

## กรณีศึกษาจริง

### 🧪 กรณีที่ 1: Mechanics (SwiftUI — N-Body Simulator)
> **ผลลัพธ์:** รายงานสรุปว่าเป็นเครื่องจำลองแรงโน้มถ่วง 2D — ระบุเอนจินหลัก `GravitySimulation.swift`, ใช้อัลกอริทึม Velocity Verlet, รองรับการชนกัน, แสดงค่าฟิสิกส์แบบเรียลไทม์
> **ไฟล์อ่าน:** 5 ไฟล์
> **สถานะ:** Build Succeeded ✅

### 🧪 กรณีที่ 2: Spring PetClinic (Java/Spring Boot)
> **ผลลัพธ์:** รายงานสถาปัตยกรรมและรีวิว — ระบุสแต็ก Spring Boot 3.4, JPA, Thymeleaf, โมเดลหลัก Owner/Pet/Visit, คอนโทรลเลอร์, การแคชด้วย JCache, ฐานข้อมูล H2/MySQL/PostgreSQL
> **ไฟล์สร้าง:** `project_architecture_report.md`, `project_review.md` ✅

### 🧪 กรณีที่ 3: Tower of Hanoi (C# / WPF)
> **ผลลัพธ์:** ตรวจสอบ Build → สร้างแผนการพัฒนา `implementation_plan.md` — ออกแบบโมเดล, เอนจิน, UI แบบโต้ตอบ, ปุ่มควบคุม, ธีม Fluent Windows 11
> **สถานะ:** Build verified ✅ → รออนุมัติแผนก่อนพัฒนา

## ✅ เช็คลิสต์คุณภาพ

- [ ] แจ้งจำนวนไฟล์ที่อ่าน/วิเคราะห์
- [ ] ตรวจสอบความถูกต้องของโครงการ (Build/Compile) ก่อนเขียน
- [ ] ระบุชื่อไฟล์ที่สร้างอย่างชัดเจน
- [ ] แยกหัวข้อชัดเจน: ภาพรวม → สแต็ก → โมเดล → ส่วนประกอบ → โฟลว์
- [ ] ใช้ชื่อคลาส/เมธอด/ไฟล์จริงจากโค้ด ไม่ใช่การคาดเดา
- [ ] เขียนเป็นภาษาเดียวกับที่ผู้ใช้ขอ (ไทย/อังกฤษ)
- [ ] รออนุมัติก่อนดำเนินการถัดไป
- [ ] แนะนำสิ่งที่สามารถทำต่อได้

## 🚀 แนวทางนำไปใช้

### เมื่อไหร่ควรใช้รูปแบบนี้?
- เมื่อผู้ใช้ขอให้ **ตรวจสอบ/วิเคราะห์โครงการ**
- เมื่อต้องการ **สร้างเอกสารสถาปัตยกรรม/รีวิว/แผนงาน**
- เมื่อจะ **พัฒนาต่อยอดโครงการเดิม** และต้องเข้าใจโครงสร้างก่อน
- เมื่อต้องการ **เอกสารอ้างอิงที่อัปเดตตรงกับโค้ดจริง**

### ทำไมถึงเป็นประโยชน์?
- ✅ **ลดความผิดพลาด:** ตรวจสอบโค้ดจริงก่อนเขียนแผน
- ✅ **สม่ำเสมอ:** ทุกโครงการได้รายงานรูปแบบเดียวกัน
- ✅ **โปร่งใส:** รู้ว่าอ่านกี่ไฟล์, สร้างอะไรบ้าง
- ✅ **ปลอดภัย:** รออนุมัติก่อนเปลี่ยนแปลงโค้ดจริง
